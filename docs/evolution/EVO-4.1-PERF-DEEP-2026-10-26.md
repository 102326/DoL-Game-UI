# 4.1 性能深度复核与 Mac 接续范围

2026-10-26。接续首轮调查，负责人要求尽量在有游戏和实机的 Windows 环境补足证据，便于之后在无游戏、无设备的 Mac 上开发。当前仍为调查阶段，没有实现优化、修改产品运行代码或发布。

## 新结论

首批 A／B 的优先级成立，但定位更具体了：

1. **A 是共用开窗的写读时序问题。** 当前证据没有显示 Vue 导航反复重挂载。面板索引、开窗判断、天气顶栏几何与焦点交接会依次触发同步样式刷新，应作为同一批次梳理。
2. **B 已有缓存，但查缓存之前的签名计算仍然昂贵。** ModHub 的更新结果缓存不会免除依赖推断成本；局部浅拷贝还使简单对象身份缓存不可靠。
3. **当前游戏编号路径也有成本。** `generateLinkNumbers → jQuery :visible` 在 UI 关闭时仍触发样式／布局刷新。它进入后续原生／协同研究，不直接判定为未经修改的原版缺陷。

优先顺序仍为：共用开窗 A → ModHub B → 持续天气 → 游戏 Renderer／原生宏等进一步研究。天气顶栏在开窗时的几何读测计入 A；持续雨效绘制仍属第二批。

## 本轮新增实机对照

输入保持为 4.0.1 / `ff428b4d385b79f6c14fada9a65301157978aa6f`、同一独立测试 App、47 个报告中的 Mod、Bedroom、自然 storm/rain/intensity=2、1363×876 CSS px / DPR 2.5。没有更新或卸载 Mod。

通过已有 UI 总开关做交错对照：属性、作弊、ModHub 各 3 轮开／关，共 18 次。这里的“UI 关闭”是调用既有总开关后的原生表现，**不是卸载 UI／Host／兼容包，也不是最小 Mod 环境**。输入与画面结构会变化，不能将耗时差全部归给某一个特效。

每次通过原按钮 `.click()` 进入，记录同步处理和随后 1.2 秒的主线程 rAF。数字是每种条件三个样本的中位数，单位 ms。

| 页面 | UI 开：同步处理 | UI 关：同步处理 | UI 开：观察内最长间隔 | UI 关：观察内最长间隔 |
| --- | ---: | ---: | ---: | ---: |
| 属性 | 102.1 | 77.2 | 116.8 | 116.7 |
| 作弊 | 82.7 | 71.2 | 300.0 | 99.9 |
| ModHub | 47.2 | 38.4 | 266.6 | 216.7 |

作弊三次 UI 开启的最长间隔均约 300ms，关闭为 99.9／99.9／125.0ms。UI 对该窗口有可复现的额外开销。属性的同步处理有所变化，但最长间隔中位几乎相同，不能把所有原生开窗都解释成同一种 UI 卡顿。

ModHub 关闭 UI 后仍为 233.4／216.7／216.6ms，支持保留 B 的第三方计算调查，不能因此认定其它 Mod 或 WebView 没有参与。

公开生命周期计数显示：属性与作弊在 UI 开启时每次增加 **1 次挂载、2 次扫描、0 次失败**；关闭时不增加。ModHub 不走这套通用面板挂载路径。两次扫描不等于两次 Vue 挂载，不能为优化直接删掉后续结构同步。

## 浏览器时间线：A 的触发点已经得到确认

新增 4 份 Chrome DevTools timeline：作弊开／关、属性开、ModHub 开。只记录目标 WebView 的浏览器事件，没有系统全局 trace、截图或录屏。用本轮专属 User Timing 标记确定页面 renderer 线程与开窗区间；其 renderer PID 不是 Android App 主 PID。

在一次作弊 UI 开启追踪中，`UpdateLayoutTree` 的调用栈与当前加载源码对上了以下位置：

| 触发点 | 单次同步样式刷新 | 当前源码 |
| --- | ---: | --- |
| 面板可见标题索引 | 66.064ms | `src/panels/main.ts` 的 `index` → `src/panels/visibility.ts` 的 `visible` |
| 开窗可见性判断 | 39.169ms | `framework/official-ui/motion.ts` 的 `syncOverlay` → `visible` |
| 天气顶栏可见性／几何检查 | 62.940ms | `framework/official-ui/weather.ts` 的 `refresh` → `showing` → `visible` |
| 开窗焦点交接 | 47.810ms | `framework/official-ui/motion.ts` 的 `syncOverlay` → 原生 `focus` |

这些是不同的 style slice；不能把它们和父级 `FunctionCall`、`RunTask` 重复相加。时间线会增加测量开销，不能拿上述单次值或整段 style 总量当成无分析器基线，也不能据此承诺相等的可优化收益。18 次普通对照与 timeline 分开采集。

属性开窗追踪也出现同一条原生 `generateLinkNumbers → jQuery :visible` 路径，其中一次 style 32.862ms、随后 layout 8.779ms。作弊关闭 UI 的追踪仍出现该路径。它需要独立核对编号范围、隐藏链接和 Mod 插入节点，不能直接跳过链接编号。

**A 的实施建议：** 将挂载／标记、可见性和几何快照、天气尺寸同步、焦点交接放在明确的更新批次中，减少写读交错。保留动态内容替换后的失效与复测，不缓存跨布局的可见性，也不延误输入阻挡或丢掉焦点恢复。具体改造仍待实施，不以删校验代替优化。

## ModHub B：现有缓存为什么没有覆盖热点

已读取当前 Loader 持有的 ModHub 1.8.3 源码，不使用另一版本替代。`javascript/modhub-market.js` 的相关路径为：

```text
getModUpdateInfo
  → getModUpdateSignature
      → getRequiredDependencies → inferRequiredDependencies
  → modUpdateChecks.get(signature)
```

`modUpdateChecks` 缓存的是更新结果；计算 key 本身仍先做依赖推断。异步结果的 `current()` 有效性判断也会重新计算该签名，不能为了命中率把这些防过期判断取消。

`findMarketModByLocalName` 遍历 catalog，对每个候选创建 `{...mod}` 后调用 `checkModInstallStatus`。所以只用 Mod 对象引用当缓存键，既可能因每次新对象而不命中，也可能因其它路径原地修改对象而返回陈旧结果。catalog 还存在多处整体替换入口，不能依赖一个未验证的“永远不变”假设。

建议先明确依赖推断的输入合同、catalog 身份索引与修订失效，再决定上游重构或可回退适配。UI 外观 Adapter 不能被静默当成任意业务补丁入口。安装状态、版本有效性与第三方回调语义继续保留。

## 为 Mac 准备的离线证据与用例

最初准备了独立的本地 `SW41-Performance-Mac-Handoff-20261026.zip`。负责人授权保存到 GitHub 后，将其可复核内容整理为[随研究分支保存的资料目录](perf-4.1-evidence-20261026/README.md)，报告保留一份，不重复上传 ZIP。公开内容不含完整游戏、存档、设备序列号、原始浏览器 trace 或私有运行数据备份。

包内包含：

- 18 次对照的数字原始记录及 timeline 主线程投影，可用 Node 内置模块复算，不依赖 ADB 或游戏。
- ModHub 1.8.3 原始源文件、限定纯函数快照、文件摘要与 MIT 署名／许可。它们是研究输入，不是可安装的替代 Mod。
- 26 个合成静态输入与 6 步同对象修改序列，冻结当前 `inferRequiredDependencies` 的输出，检查输入不被修改及返回结果不互相污染。
- 两个故意错误的缓存反例：仅按 Mod 对象引用缓存、仅按 catalog 引用与 Mod 内容缓存。它们分别在修改序列第 1／4 步被拒绝，证明用例能发现实际缓存失效问题。
- 当前关键 UI 源码身份清单与核对脚本，以及本报告和操作说明。

纯函数用例在 Windows Node 26.12.1 通过。它们保存的是当前函数行为，不宣称所有描述解析都是正确业务规格，也不覆盖完整依赖合并、安装／更新和异步版本服务。性能改造应先保持此行为；发现真实业务缺陷时单独归因、修复和审查，不能修改 golden 结果来掩盖性能改造回归。

原函数的合成计数实验中，250 项 catalog、10 次调用产生 60480 次动态 `RegExp` 构造，100 项为 24480 次，25 项为 6480 次。这里只证明该路径重复构造与规模增长，不代表引擎每次都重新编译正则；Node 耗时不等于 Android 开窗耗时或未来节省量。

## 不依赖游戏的浏览器验证

在当前 Windows Edge / Node 26.12.1 上实际执行了仓库已有的：

- `node tests/evolution-panels.cjs`：6 种通用面板、3 个缩放档的坐标断言，原生动作保留与清理，退出码 0。
- `node tests/official-game-motion.cjs`：单次原生派发、100／80ms 窗口节奏、原命中、表单、打断、总开关／reduced motion 和清理，退出码 0。

这些用例执行真实自有模块与受控 DOM，不需要游戏。Mac 可在安装项目依赖及 Playwright Chromium 后复用；Windows 实测不等于 Mac 已运行，也不等于真实游戏验收。需要的源码和产物准备命令见接续包 README。
