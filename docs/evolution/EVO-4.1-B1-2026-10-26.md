# 4.1 首批 B1 — 不可变规则复用与容量反例

2026-10-26，与[A1](EVO-4.1-A1-2026-10-26.md)分开提交。B1是本批对计划B离线切片的简称，不代表新增正式产品能力编号。

结论：受控输入等价，缓存装得下时重复推断有局部时间收益；超过容量时仍有退化，保持离线候选，不接入ModHub，不判定整体性能通过。A1的时间负结果同样保留，当前没有可以直接宣布解决Android开窗卡顿的优化。

## 已实现和验证

1. 复核1.8.3实际调用：`getModUpdateInfo` 在查询已有缓存之前构造 `getModUpdateSignature`，其中执行 `getRequiredDependencies`／推断；异步 `current()` 也重新核对签名。`findMarketModByLocalName` 返回浅拷贝。不能按对象引用缓存依赖结果，不能跳过签名或异步过期防护。
2. 从冻结函数精确复用别名三条正则，只留字符串→无g/y规则，不缓存任何业务结果。每次读取最新描述、bootNames、身份与别名，重建冲突表与返回值。1024项／256字符上限；大目录保留原匹配构造路径。
3. 原 `check-inference` 的26静态场景／6步同对象修改、输入不变、消费者隔离通过。新增1276个状态对照及容量／长别名检查通过。原golden、源包及21条摘要保持不变。
4. 新MTS纳入既有严格研究类型配置。`npm run ci:check` 在加入候选后退出0；最终追加容量测量及回退修改后，冻结合同、新检查器与 `tsc -p tsconfig.research-tools.json` 再次退出0。A1产品代码未再变化，复用其三个浏览器合同。
5. 独立审查修复计时公平性P2：旧版复用基线函数、每对新建候选，热度不对称。最终双方每对新建，等量预热，交替顺序；旧数据不用于结论。

## 不能隐藏的容量反例

初版1024项LRU遇400项合成目录／1608个有效别名，会在每个分句循环驱逐。热10次双方均构造96480条正则，原中位数101.035ms、候选129.920ms。此版没有全绿验收，被保留为[拒绝数据](perf-4.1-candidates-20261026/rejected-churn-result.json)。

修订后在既有 `names.size > 1024` 时不进入缓存，工作量回到原构造路径且缓存构建为0。**这只修复了缓存抖动，不能推导耗时相等**；最终实测大目录仍更慢，如下表，不为通过而放宽时间阈值或删去400档。

## 最终成对时间结果

macOS27.0.1 arm64／Node26.12.1；仅纯函数合成输入。冷列每次首次推断，热列每组10次推断，之前双方各预热10次。每档12对，两对预热数据丢弃；中位数为中间两值平均。未启动浏览器／timeline，VM创建不计时，进程与引擎缓存未清空。

| 目录条数 | 冷：原→候选 ms | 热10次：原→候选 ms | 热路径配对差值中位数 ms |
| --- | ---: | ---: | ---: |
| 25 | 0.826→0.868 | 5.647→2.492 | -3.116 |
| 100 | 2.675→2.412 | 21.843→8.935 | -13.542 |
| 250 | 5.613→5.104 | 58.307→22.854 | -35.397 |
| 400（容量回退） | 10.509→10.824 | 117.912→136.565 | +9.607 |

25／100／250档热10次的正则构造从6480／24480／60480降为0；400档仍为双方96480，缓存为0。构造计数不等于引擎编译次数。小目录首次推断也不保证更快。独立中位数之差与配对差值中位数并不相同，逐对数据全部保存，未按有利结果挑轮次。
