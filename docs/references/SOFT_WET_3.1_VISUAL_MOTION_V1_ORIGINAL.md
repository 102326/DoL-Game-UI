# Soft and Wet 3.1

## 视觉与动效推进口径

产品目标纠偏与后续评审建议　V1.0

2026年10月21日　｜　撰写 小鸥　｜　供项目负责人及 ChatGPT 复核

## 一 结论与本稿状态

建议采用负责人最新澄清的口径：快速流畅、华丽精致、感知舒服共同构成产品目标。允许有价值的新特效增加合理等待，不等于授权降级特效。

Soft & Wet 是偏向展示型的 UI Mod。让用户明显感受到精心设计的视觉与交互，是产品价值本身，而不是在工程稳定之后可有可无的装饰。不能把“升级”默认理解成缩短时长、减小幅度、删去层次，或以更少改动作为主要成果。

本稿建议纠正此前执行及审核口径中的偏差，同时保留已经取得的可靠性成果。下一步应先明确可观察的视觉目标，再用原速对照、实际交互和运行证据判断是否值得采用，而不是先决定所有效果都要更轻、更短。

### 需要明确纠正的两点

• 此前将“新特效造成等待”理解为应优先削弱或降级特效，属于对负责人原意的误读。本稿明确撤回这种解释。

• 此前将“局部改善、尽量保留原逻辑”作为默认范围，也不能继续作为硬性限制。负责人已允许静态与动态效果重做，允许部分乃至大量逻辑重写。

这不只是在要求 Codex 调整方向，也是在纠正我此前审核中可能加入的保守前提。技术审核仍应指出具体故障与代价，但不能把个人偏好的克制、短促或最小改动替代产品目标。

### 当前仍是复核稿

本稿供负责人和 ChatGPT 先确认口径，不代表已经批准某一新视觉方案，也不构成恢复实现、合并或发布的授权。当前暂停新增功能的状态不因这份报告自动改变。确认口径后，再由负责人确定具体方案与实施范围。

## 二 负责人的原始表述与正确解释

以下为负责人于 2026年10月21日的原话，保留原有措辞；第三段澄清优先解释第一段中“合理降级”的含义。

### 产品目标

我的理解是:1.快速流畅,不能凭空增加不应该出现的等待时间,如果是新加特效导致的可以合理降级2.华丽精致,得让用户看得出来这个UI足够炫酷,是下了狠功夫的高质量UI3.感知舒服,让用户感觉不到自己在等待,有足够强的流畅性

### 重做权限

现有的动态静态特效如果有更好看的效果,更优雅的展示,或是更好的性能释放,我们都可以重做,UImod作为偏向展示型的mod允许大改动,允许重写部分甚至大量逻辑

### 对等待时间的澄清

如果是新加特效导致的可以合理降级,这句话意思是允许新特效增加等待时间,而不是降级特效

### 据此采用的解释

“快速”不等于全部动画都取最短时长；“华丽”不等于堆满粒子、模糊或夸张位移；“舒服”也不等于完全看不见动态。三者需要通过具体场景的节奏、层次、运动连续性和反馈关系共同实现。

有明确视觉收益的新特效，可以增加展示时长，必要时也可以增加合理的功能等待。判断重点是这段时间是否有价值、用户是否感到动作正在顺畅发生，以及连续使用时是否仍然舒服。不能凭空插入停顿，也不能因为超过旧版时长就判定失败。

本稿不设统一毫秒上限，不预设“业务绝不能等待动画”，也不把每次新效果都必须与旧版等时长作为门槛。反过来，允许等待并不等于允许任意锁定操作、动画排队、卡顿或丢失输入。具体取舍由可观看的方案和负责人反馈决定。

## 三 对本批工作重心的判断

审查对象仅为 #22 研究分支的 50b491d → b507f1a，不把整个分支相对 main 的历史差异算入本批。根据已核对的差异与 Codex 的对审说明，本批应定性为“既有动效基础修整、可靠性修正与评审演示设施”，而不是已经完成窗口或全局视觉升级。

### 执行重心确有偏移

设置分类从 620ms 缩为 360ms，较大位移、旋转、模糊与裁切被简化；已识别原生面板的真实窗口移动被去掉，主要改成淡入，材质代理运动也明显减弱。这些选择可能让操作更利落，但其主要方向是“更短、更轻”，并不自动等于“更华丽、更精致”。

负责人反馈新窗口与原版看不出明显区别，与这批实际改动的性质一致。问题不是必须重画布局、换颜色或加框架，而是未先建立足够明确、可观察的新运动表现，就将基础修整概括为升级完成。

### 保留工程价值 不让它替代视觉验收

• 隐藏页与卸载取消、代理所有权、旧回调清理以及缩放换算，属于有价值的可靠性工作。是否纳入正式版本，仍应按实际影响补验证。

• 缩短时间、取消旋转或模糊属于设计选择，不应因为测试通过就自动保留；也不应因为本次纠偏而机械恢复所有旧参数。

• 共享 sourceMotion 影响多个调用方。不能以“没有直接改页面文件”推断其它场景不受影响。

Codex 后来的对审说明已经收紧成果表述并承认新窗口未获视觉验收，这一纠正是必要的。这里评价的是执行目标与成果分类，不推断其动机，也不否认已经完成的基础工作。

### 成果不能跨范围继承

sphere.ts 与 hub-motion.ts 不属于这批新增改动。已获认可的球体效果不应重新包装成本批成果，也不等于正式游戏中的完整 Hub、窗口或其它场景已经获验收。后续表现依负责人最新方案确定，不在本稿重新发起旧方案投票。

当前演示包含受控模拟原生面板；新版本单独录屏不等于新旧同操作对照。研究分支测试通过，也不等于真实游戏联合运行、设备表现或生产合并条件已经满足。

## 四 后续设计与技术取舍口径

### 把响应 展示 与可操作时机分开设计

每个交互都应说明三个时点：输入何时被明确回应、目标内容或操作何时可用、视觉余韵何时结束。三者可以重叠，也可以因设计需要部分串联，不要求整段演出结束后才开始一切，也不一律禁止功能等待。

例如窗口可以先回应点击，再让材质与内容按层次展开，最后自然稳定；若某一段需要暂缓操作，就说明它在视觉或状态上的理由，并处理再次点击、关闭和反向输入。最新意图不能被一长串过期动画淹没，购买、保存等业务也不能因重复输入或取消处理而出错。

### 以可感知的质量评价华丽

可重点观察来源与落点是否清楚、主次层是否分明、加减速是否有力量、阶段交接是否自然、材质与内容是否共同构成空间，以及连续操作是否保持动作完整。精致可以来自克制的细节，也可以来自鲜明的演出；不能预先把低强度当作唯一正确答案。

性能优化优先研究重复材质、无效绘制、坐标测量、资源释放和运动组织。不能把性能问题一律归结为特效太多，也不能在缺少证据时宣布某种库或渲染方式必然更快。主动选择减少动态的用户仍应得到合法可用的表现，这不等于把默认效果擅自降级。

### 允许重构 但要说清楚收益与影响

可以重做现有静态与动态效果、重排视觉层、改写动画及交互逻辑，必要时进行较大范围重构。新框架、SVG、数学轨迹、WAAPI 或其它合理技术都可比较；不强制 GSAP，也不因 CSS 理论上可实现就否决成熟工具。

真实控件是否移动、材质代理如何组织，应由方案与正确性共同决定，不把“只有装饰层能动”固定成所有窗口的规则。大改动需列清受影响场景、业务合同与验证办法；代码量和依赖数量本身既不是否决理由，也不是品质证据。

继续保持 Host＋UI 双包、现行 3.x Acrylic 视觉身份、业务与存档语义及第三方兼容合同，除非负责人另行改变这些目标。允许视觉重做不等于必须更换配色、布局或全部控件，也不自动扩展到 3.5／4.0 的新产品功能。

## 五 建议怎样推进与验收

### 先建立一个能被看见的设计判断

口径确认后，建议先选一个代表性窗口做动作分镜：从哪里出现，材质与内容怎样分层，分类切换怎样交接，关闭怎样收束，快速反向怎样接续。每个阶段写出负责人能直接观察的特征，而不是只列动画库与时长参数。

以同一操作、同一设备及视口、相同缩放和原速录制旧版与候选版并排对照，覆盖首次打开、连续切换、关闭与中途反向。完整展示过程不裁掉等待，不加速掩盖拖沓；慢放可作为补充，不替代原速判断。

选择一个窗口是降低试错成本的验证方法，不是后续只能小修一个窗口的范围上限。负责人认可后，可以按收益扩展到其它窗口和页面，也可以批准更大规模重构。范围由实际效果与产品决定，不由“改动应尽量小”预先封顶。

| 验收线 | 回答的问题 | 本批应如何表述 |

| 视觉验收 | 是否明显更精致、更炫酷，节奏和等待是否舒服 | 新窗口未获负责人认可；球体认可单独记录 |

自动测试证明其覆盖范围内的正确性；负责人决定视觉品质及等待取舍。两者不能相互冒充。原型、集成候选和正式交付要使用不同状态，不能因为样片好看就跳过工程验证，也不能因为测试全绿就宣布视觉目标完成。

### 请确认的推进口径

建议确认：采用本稿对合理等待、展示品质与重构自由的解释；停止把“短轻稳”当作唯一升级方向；保留可靠性成果的独立评估；下一步先形成可观察的新方案与原速对照，再批准具体实施范围。确认前不恢复新增功能，不合并或发布。
