# 第一章：正式研发决定

## 1.1 项目升级

Soft & Wet 原 3.1 Motion Evolution 方向正式提升为 **4.0 — Evolution**。

4.0 不再定位为局部动画优化，而是一次完整的：

**视觉基础架构、动画运行管理与产品表现品质的共同进化。**

本版本必须同步解决：

1. 动画及视觉资源管理分散的问题；
2. 相同职责存在多份独立实现的问题；
3. 跨界面行为和视觉表现不一致的问题；
4. 天气、材质、Floating Hub 等核心特效质量不足的问题；
5. 中断、反向、重定向、资源释放及兼容性方面的可靠性问题。

## 1.2 项目负责人最高决定

**长痛不如短痛。**

本次研发不以 Codex 额度、代码改动量或短期开发工作量为主要限制条件。

允许：

- 大规模调整现有 UI 架构；
- 重构或者必要时重写相关子系统；
- 统一长期分散的实现；
- 引入能够提高视觉质量或可靠性的成熟技术；
- 建立自动化验证与诊断设施；
- 制作并比较多种视觉原型；
- 删除经验证已完成迁移的冗余旧路径。

但不允许为了展示架构复杂度而建设缺乏实际用途的新平台。

**目标是有效偿还架构债务，不是最大化代码重写比例。**

## 1.3 正式施工授权

项目负责人正式授权 Codex 开始 Soft & Wet 4.0 的研发工作。

授权包括：

- Phase 0 源码复核、范围冻结与基线采集；
- 架构重构和共享实现建设；
- 动画与视觉资源统一管理；
- 天气视觉原型研究；
- Golden Spin 与真实 Floating Hub 联动研发；
- 必要的测试工具、CI 规则和开发期诊断能力；
- 在独立开发分支提交、构建与验证成果。

**本授权不自动包含合并 main、修改对外 Host API、发布正式版本或改变已批准的产品设计。**

这些操作仍须获得负责人明确许可。

# 第二章：第一大纲——交互体验三项纲领

本章为 Soft & Wet 4.0 的最高产品体验准则。

架构、动画、渲染技术和工程组织均须服从本章。

## 2.1 快速流畅

用户的每次操作都应及时得到明确反馈，不应丢失，并且能够合理处理中断、反向与连续操作。

为了更好的视觉体验，可以接受一定的资源、性能和演出时间成本，但应通过合理的技术实现、动画编排与性能优化，避免明显的输入延迟、交互卡顿或无意义的等待。

**动画可以有完整的演出过程，但不得仅仅为了等待动画结束，而不必要地阻止用户继续操作。**

对于确实需要等待的业务或状态转换，应明确其必要性，并提供连续、清晰的视觉反馈。

快速流畅不代表所有动画必须短。

天气材质的长期变化、金属球的蓄势与收束、光影余韵等，均可根据设计价值拥有适当的演出时间。

但新的输入意图应得到正确处理，而不是无条件等待旧动画结束。

## 2.2 华丽精致

用户应当一眼看出，这套界面经过了高水准的设计和打磨。

品质来自光影、材质、运动和细节的整体一致，而不是特效的数量。

界面静止时同样耐看，看第一百次也不让人厌倦。

低频的关键时刻可以有强烈的视觉冲击，高频操作则保持精致、克制。

允许大胆引入：

- 高品质 Acrylic 与动态材质；
- 成熟的动画编排系统；
- 复杂光照及表面视觉；
- Canvas、WebGL 或 Shader；
- 高精度运动模型；
- 多阶段、可中断的动态演出。

技术实现方式不作为视觉品质的替代指标。

**最终以实际观看、交互手感及运行表现验收。**

## 2.3 感知舒服

让用户尽可能感觉不到自己在等待。

必要的处理时间应转化为连续、自然、带有信息的界面变化，而不是没有反馈的停顿。

交互遵循四项原则：

**可预期：** 用户理解内容从哪里来、到哪里去。

**不打扰：** 不无意义地晃眼、制造眩晕或持续抢夺正文注意力。

**可掌控：** 动画不无理由绑架操作，能够按交互语义被中断、反向、重新定向或结算。

**诚实：** 不伪造操作成功；进行中的状态明确显示为进行中。

## 2.4 冲突优先级

发生冲突时：

**输入被接受 > 必要的业务与交互正确性 > 内容可读、可操作 > 演出完整度 > 特效强度**

输入被接受，不意味着每个点击都必须立即执行，也不意味着所有事件应无限排队。

业务是否允许执行、是否应合并重复输入，应由真实状态与操作语义决定。

**华丽可以占用演出时间，但不能无理由占用用户的操作时间。**

# 第三章：4.0 核心架构目标

## 3.1 统一管理

Soft & Wet 自己拥有的视觉与动画资源，必须逐步纳入统一、可审计的管理合同。

重点包括：

- 所有者与生命周期；
- 动画状态和目标；
- 取消、结算、中断与接续；
- 过期回调保护；
- 属性写入与资源归属；
- 坐标及缩放处理；
- 渲染资源释放；
- 开发期追踪与异常诊断。

允许 GSAP、WAAPI、CSS、SVG、Canvas 等技术共存。

但每种技术必须具有清楚的资源所有权与生命周期边界。

**统一的是管理合同，而不是强制所有动画使用同一个引擎。**

禁止无差别接管游戏原生或第三方 Mod 创建的动画及资源。

## 3.2 同构复用

**相同职责不应长期存在多份互不关联的实现。**

应根据实际行为和来源，判断哪些能力能够共享。

优先考虑：

- 导航挂载与清理；
- 窗口基础状态及生命周期；
- 统一坐标服务；
- 动画作用域及失效回调；
- 同类 Acrylic 材质角色；
- 环境参数读取及消费；
- 共同的资源管理和追踪。

不要求所有窗口统一为一个 Vue 组件。

特别是原生 dialog、商店购买区、衣柜真实节点、设置工作区、Floating Hub 等，必须保留各自合法的宿主与业务语义。

## 3.3 异构自由

不同场景可以拥有不同视觉语言。

例如：

- 天气：持续、连续、具有材质余韵；
- Floating Hub：蓄势、回旋、释放和能量传递；
- 分类切换：有方向和层次的空间交接；
- 状态反馈：局部、准确、具有因果关系；
- 特殊场景：允许更强烈的动态演出。

不得为了统一管理，将所有交互简化成相同的淡入淡出。

## 3.4 架构实施原则

优先复用已有能力：

- Host owner 与挂载合同；
- surface 管理；
- `sourceMotion`；
- 已有共享导航及焦点能力；
- 已有天气读取；
- 研究分支中的有效动画成果。

Claude 提出的四层结构可以作为职责参考：

- 统一运行管理；
- 平台服务；
- 共享原语；
- 场景演出。

但**不强制创建四个新包、一个万能 WindowShell 或庞大的中央 Runtime**。

架构设计应依据真实消费者和实际故障模式确定。

# 第四章：架构研发线——Architecture Evolution

本线目标是集中偿还已确认的架构债务。

## A0：完整范围审计与迁移基线

在首次大规模修改之前，Codex 应核对当前源码身份与正式运行路径。

建立《4.0 架构覆盖与迁移清单》。

每个相关消费者至少记录：

| 字段 | 内容 |
|---|---|
| 消费者 | 实际模块或界面 |
| 当前入口 | 正式代码位置 |
| 管理能力 | 生命周期、动画、坐标、材质等 |
| 当前实现 | 已共享、重复、独立或待确认 |
| 迁移决定 | 纳管、收敛、保留或例外 |
| 例外理由 | 真实业务、宿主或技术约束 |
| 验收方式 | 对应测试与运行证据 |
| 旧路径退出 | 删除、保留适配或后续处理条件 |

不能只登记属性和社交两个页面。

必须覆盖经源码审计确认属于 4.0 范围的自有 UI 动画、材质与视觉管理消费者。

**覆盖范围在 A0 结束时提交负责人确认，之后作为架构发布关卡的正式依据。**

避免未审计即宣称全仓库百分之百纳管。

## A1：首个工程切片

优先采用小鸥建议的真实同构族：

**属性导航 + 社交导航。**

研究并实现共同的 NativeOverlayNavigationAdapter 或等效共享能力。

共同管理：

- 原生 overlay 发现与身份；
- 导航挂载和 Host 租约；
- observer 与调度；
- 状态世代及回调失效；
- 资源释放及失败恢复；
- 必要的坐标和动画管理。

保留：

- 游戏原生正文节点；
- 两类导航各自的识别逻辑；
- section 语义；
- 页面专属动画和样式；
- 原生业务事件。

### A1 验收条件

必须证明：

1. 两个消费者确实进入共同实现；
2. 相同职责不再各自维护不同的基础逻辑；
3. 原生节点和业务事件语义未改变；
4. 快速切换、反向、卸载、重挂和异常恢复正确；
5. CSS Zoom、滚动与坐标变化正确；
6. 相关资源可清理；
7. 一处共享修复能够在两个实际消费者上生效。

建议保留共享实现的运行记录、正反测试及必要的故障注入证据。

**A1 完成只是证明架构路线可行，不代表 4.0 架构研发完成。**

## A2：统一管理能力推广

将 A1 证明有效的机制推广至 A0 已批准的目标消费者。

重点处理：

- 自有动画创建与作用域管理；
- GSAP、WAAPI、CSS 等不同执行方式的接入；
- 共享生命周期；
- 属性所有权及重定向；
- 坐标、缩放和视口；
- 资源释放与运行追踪；
- 已确认重复的材质与窗口基础行为。

复杂场景可以保留专用控制器，但必须符合共同管理合同。

不强行要求简单透明度动画具有物理速度积分。

不以禁止合法 CSS 或 Vue 能力的方式伪造统一覆盖率。

## A3：历史路径退出

本次重构的重要目标之一，是减少长期并存的重复实现。

对已完成迁移的同构族：

- 删除确实冗余的独立实现；
- 删除失去用途的过渡适配器；
- 清理临时研究副本的正式入口歧义；
- 阻止已迁移消费者重新绕回旧路径；
- 为有意保留的例外记录理由。

**不得将“以后再整理”作为重复架构永久存在的默认结果。**

但某个独立实现确实承担不同业务或宿主语义时，可以作为批准的例外保留。

# 第五章：视觉研发线——Visual Evolution

视觉研发与架构研发明确并行。

**不得等整个统一管理体系建设完成，才开始制作天气与 Floating Hub 的视觉原型。**

研究原型可隔离实施；正式集成时必须接入已经稳定的管理合同。

## V0：视觉基线冻结

保留已批准的表现：

### 设置 V2.3

- 打开 100ms；
- 关闭 80ms；
- 简单透明度过渡；
- 正文立即可交互；
- 分类保留已认可的 V2.2 演出。

不得擅自恢复复杂打开、关闭特效。

### Floating Hub 铁球

- 保留已认可的金属球外观；
- 不恢复被否决的星形刻纹；
- 不添加未经批准的轨道、星环或新菜单布局；
- 球体自身旋转是视觉主体；
- 保留真实工具和最终布局。

### Acrylic

保留现有视觉身份与必要材质层次。

不得将所有嵌套 blur 无差别删除。

## V1：天气与 Acrylic 环境视觉重制

这是 4.0 的核心视觉研发任务。

保留现有 `window.Weather` 权威输入、共享读取、既有 fallback 语义及真实宿主边界。

研究目标：

- 更高品质的光照和 Acrylic 氛围；
- 水滴、水痕、湿润和凝露；
- 雪与局部霜纹；
- 光照、色温及材质的自然变化；
- 不同材质表面消费统一环境参数；
- 中途天气变化的合理接续；
- 稳态时长期耐看的画面。

允许 CSS、SVG、Canvas、WebGL 或 Shader 方案比较。

### V1 最低演示场景

必须至少提供以下可观看的真实场景：

**场景 W1：晴天 Acrylic。**

展示静止状态下的玻璃质感、光照和环境氛围。

**场景 W2：晴天转雨。**

在同一 Acrylic 表面上展示从晴天进入雨天后的动态材质变化，而不仅是旧天气层交叉淡化。

**场景 W3：晴 → 雨途中转雪。**

在雨天演出尚未完成时改变目标天气，展示自然接续，没有明显回到固定首帧、残留旧天气或突兀跳变。

**场景 W4：持续使用。**

天气特效稳定运行，用户正常操作、切换页面与恢复可见性时，视觉状态和资源管理保持合理。

上述场景先在可控环境中验证，再进入真实游戏与目标设备验收。

**原型通过不等于正式交付完成。**

## V2：Golden Spin 与真实 Hub 联动

保留已认可的球体造型。

视觉研发重点：

- 球体蓄势；
- 加速回旋；
- 角速度和旋转轴变化；
- 金属表面光照；
- 必要的残影及运动线索；
- 释放与自然收束；
- 拖动、停靠、关闭及中途反向；
- 球体运动与实际工具菜单之间的能量联系。

### V2 最低演示场景

**场景 H1：球体展开真实工具。**

由已认可的球体驱动真实 Floating Hub 工具展开，工具最终落到原有布局。

**场景 H2：完整收束。**

真实工具以合理顺序回收，球体完成视觉收束，状态正确。

**场景 H3：中途操作。**

展开、收束或拖动过程中发生新输入时，动画和工具行为正确衔接。

**场景 H4：正常使用。**

工具可正确激活，焦点、停靠、拖动和资源生命周期没有回归。

不接受仅展示一颗漂亮的独立旋转球，就宣布 Hub 联动完成。

## V3：其它视觉进化

在核心视觉任务进展稳定后，继续研究：

- Acrylic 材质细节；
- 导航与分类切换；
- 窗口及抽屉动效；
- 局部操作反馈；
- 其它具有明确改善价值的静态和动态表现。

角色状态变化的高级特效仍属于未定型候选。

不因版本升至 4.0 就自动将所有视觉创意纳入发布门槛。

# 第六章：动画期间操作与必要等待

本章是第一大纲的强制实施要求。

**不允许仅以“动画尚未结束”为理由阻止操作。**

对于确实需要临时限制操作的场景，Codex 必须记录：

| 项目 | 必须回答 |
|---|---|
| 限制对象 | 哪个操作或控件暂不可用？ |
| 限制原因 | 业务、状态或交互上为什么必要？ |
| 解除条件 | 何时恢复？以什么真实状态为准？ |
| 新输入处理 | 关闭、反向、重复点击时怎么办？ |
| 视觉反馈 | 用户怎样知道当前仍在进行？ |
| 异常处理 | 取消、失败、卸载或超时怎样恢复？ |

### 具体原则

- 输入不应因动画时长而无意义丢失。
- 可合理合并重复输入，采用最新目标或拒绝不合法操作，但必须符合该控件语义。
- 已提交业务与未提交业务的动画反馈必须区分。
- 不允许过期回调覆盖新状态。
- 真正的模态与原生业务限制应受到尊重。
- 合法取消、关闭或反向应具有明确处理路径。

**输入被接受，不等于所有点击都必须排队执行。**

长演出是视觉设计自由，不是交互锁定许可。

# 第七章：性能与画质原则

4.0 不将自动降低效果档位设为默认产品目标。

Codex 必须优先考虑：

1. 消除不必要的计算和重复绘制；
2. 正确暂停无须运行的资源；
3. 优化动画所有权与调度；
4. 减少无意义的布局与合成开销；
5. 比较能够保持同等视觉品质的实现；
6. 在真实设备上验证性能。

### 性能验收

至少覆盖：

- 输入反馈和交互响应；
- 动画流畅性及明显卡顿；
- 同时存在多个窗口与环境特效；
- 长时间使用；
- 页面隐藏与恢复；
- 资源释放和重复操作；
- CSS Zoom、DPR 与尺寸变化；
- Android WebView 与桌面浏览器。

具体帧率阈值、测试设备及兼容范围，应在 A0/V0 阶段结合真实环境确定，不虚构已经完成的指标。

### 画质取舍

如果某项效果确实无法在目标环境中以批准品质稳定运行：

- 提供性能证据；
- 提供原始效果与替代方案对照；
- 明确画质差异；
- 说明继续优化的可行性和代价；
- 交由项目负责人裁决。

**未经批准，不得以隐性自动降档的结果冒充完整视觉验收。**

浏览器能力不足或渲染资源异常时，可以采用保证基本功能可用的必要兼容路径，但必须清楚报告其视觉差异。

# 第八章：统一管理与可靠性验收

4.0 的架构验收不只检查模块是否存在。

必须验证共同实现真正发挥作用。

建议综合采用：

- 静态依赖与消费者清单；
- 运行时 consumer/implementation 追踪；
- 共享原语契约测试；
- 针对性故障注入；
- 正常与异常生命周期测试；
- 输入及回调重入测试；
- 可观察业务行为对照；
- 视觉基线与真实画面对照。

### 必须防止的错误

- 多个控制器同时修改同一属性；
- 过期动画覆盖新目标；
- 卸载后资源仍保持活动；
- 关闭后无法重新打开；
- 动画完成却未解除合法交互限制；
- 异常路径未释放 Host 租约；
- 原生业务事件被重复触发；
- 旧节点被错误恢复；
- 缩放和坐标变换不一致；
- 为统一材质引入新的重复背景采样。

对于已完成迁移的范围，必须能说明：

**哪些消费者共享了什么，以及怎样证明它们真的在使用同一实现。**

不承诺所有界面从此绝对没有 Bug，但必须显著减少已确认的重复架构债务。
