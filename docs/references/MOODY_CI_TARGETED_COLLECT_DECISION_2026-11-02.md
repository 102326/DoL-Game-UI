# Moody Blues CI 精准选测与集中播报补充决议

整理日期：2026 年 11 月 2 日  
用途：交接给 UI Mod 对话中的 Codex，修订 CI 研究与规划方向

## 一 最新决议与适用范围

我们希望 Moody Blues CI 更像“手术刀”：日常围绕实际改动精准验证，大版本最后封板时进行全量验收。运行中发现错误，不应立即结束整轮，而应尽力完成本轮范围内仍可执行的检查，再一次性汇总根因、影响和修复建议。

这是用户最新确认的方向。**本补充取代此前日常可采用 fail-fast 的候选建议，并进一步明确普通 PR 或普通 RC 不默认触发全量验证。** Soft & Wet 4.2 的体验研究、自定义边界、Host 和性能方向保持不变。本次只形成补充报告，不修改代码、工作流、分支规则或仓库设置，也不代表相关配置已经迁移。

| 类别 | 本次状态 |
| --- | --- |
| 日常与 PR 精准选测 | 已确认方向，依据改动及影响范围选择必要检查 |
| 大版本最后封板全量验收 | 已确认方向，典型节点为 4.1、4.5、5.0 最后候选提交 |

## 二 日常与 PR 围绕影响范围选测

精准选测不能只看被改文件，也不能退化成每次跑全部。建议把**改动本身、直接依赖、间接消费者和相关历史回归**共同作为选择依据。例如，共享输入派发改变时，应覆盖受影响的焦点、命中与交互消费者；仅调整独立视觉参数时，则不应无理由回放所有历史研究候选。

实现上优先维护少量能读懂的模块关系和检查映射，说明为什么选中、为什么不适用。不要为选测再建设大型框架，也不要用庞大目录、层层审批或复杂评分增加维护负担。已有映射能表达的关系直接复用；无法可靠判断影响范围、触及共享核心或选择规则自身时，保守扩大覆盖，必要时全量。

“选中范围较小”和“验证要求变松”必须分开：被选为本轮必需的检查仍须实际完成。缺报告、零有效断言、未处理页面异常、取消和未知状态不能被当成成功。不适用应给出理由，不能用 skipped 包装一次并未执行的通过。

## 三 全量主要放在大版本最后封板

全量验证主要集中于 4.1、4.5、5.0 这类大版本的最后候选提交和封板验收，而不是每个 PR、每次普通 RC 或每个小修复。遇到影响范围不可确定、共享核心重大变动、构建链或验证体系变化等情况，仍可以依据风险提前扩大到全量；这里不是禁止全量，而是让它有明确理由。

建议先定义“本版本全量”所承诺的产品、设备、包合同与回归集合。现役支持范围应覆盖完整，退役实验不应仅因历史存在就永久成为每轮全量的必需项。CI、实机和人工视觉验收承担不同责任，机器通过不能代替真实体验判断。

封板后若有修复，应绑定新的实际提交，列明差异与影响，再进行风险匹配的复测。不能让旧报告冒充覆盖新 SHA，也不要求每次修复都无条件从头全量重跑。是否需要重跑全量，应由差异是否破坏原证据适用性、影响范围及发布责任决定；最终发布证据必须能明确追溯源码、产物与验证身份。

## 四 检查尽量跑完 错误按根因一次汇总

本轮已经选中的独立检查，应在其他检查失败后继续执行，尽量一次找到更多问题。若前置条件已失败，导致后续检查无法有效执行，应标为 **BLOCKED 或未运行**，说明阻塞原因；既不能记为 PASS，也不能把由同一失败造成的缺产物、缺截图和缺报告制造成多个独立产品缺陷。

致命环境无效、资源耗尽或安全风险可能使某条执行分支无法继续，此时可以停止这条不可用分支并保留首个原因；其他仍然安全、独立且可执行的检查应继续。不能为了“跑完”在无效环境里产生大量没有意义的错误。

“把所有错误找到”应理解为：**在本轮选定范围、可执行条件和既定超时内尽最大努力收集，不保证证明所有缺陷都已发现。** 不采用自动重试直到变绿的方式消除失败；若确有必要重试，应保留原失败、重试理由和各次结果。

建议最终集中报告至少包含：

- 范围总览：选中、已执行、通过、失败、阻塞、未运行的数量与清单，说明统计关系，避免重复计数。
- 根因分组：区分产品、夹具、基础设施问题，列出关联检查与下游影响，不以红灯数量代替缺陷数量。
- 每组证据：实际提交与运行身份、关键日志或截图、复现条件、建议修复方向和建议复测集合。
- 整体结论：哪些必需检查失败或未完成，哪些证据可用，哪些问题仍阻止进入下一阶段。

集中播报不意味着执行期间必须完全沉默。进度、诊断日志和必要阻塞提醒可以持续提供；最终再给出一份统一、去重、可行动的结果，避免逐个错误反复催促修复，导致尚未完成的检查被频繁打断。**继续收集错误不等于允许失败通过：必需检查失败或未运行，仍须阻止最终 gate 成功。**

## 五 既有配置与迁移边界

原 CI 评审基于 4.1 研发提交 `9c26b0090fa21ea389c11f0471a79d5af45a577d`；当时 main 为 `ff428b4d385b79f6c14fada9a65301157978aa6f`，版本仍为 4.0.1。这只是原评审快照，本补充没有重新审计在线配置，也不据此判断当前 4.1 是否已发布。[原研发基线](https://github.com/102326/DoL-Game-UI/tree/9c26b0090fa21ea389c11f0471a79d5af45a577d)

该快照的 required checks 为 `validate` 与 `moody-gate`；research 不在该 required 列表，但当时 4.1 候选政策仍要求 standard 与 research 双流程。平台规则和项目政策是两层约束，不能自行把其中一层当成无效。原文档已有按有意义批次运行完整 CI 的政策，本次是在此基础上进一步明确精准选测、封板全量和集中播报方向。[CI 政策快照](https://github.com/102326/DoL-Game-UI/blob/9c26b0090fa21ea389c11f0471a79d5af45a577d/docs/CI.md)

迁移前不绕过 required checks，不用路径跳过造成永久 pending，不以跳过必需项后 gate 变绿冒充优化。精确身份、反假绿不变量及已有候选约束应保留，配置和政策如何调整需另行确认。

## 六 建议 Codex 先交付的研究方案

建议 UI Mod 对话中的 Codex 先核对当前基线与上述快照差异，再给出一份简洁方案：列出少量影响映射及不确定时的回退规则；说明日常、普通 RC、大版本封板各选哪些检查；设计独立检查继续、依赖检查阻塞和根因汇总的行为；明确封板后差异复测、证据身份及迁移验收方法。

方案应区分已经确认的产品方向与尚待选择的技术实现，并列出需要修改的范围、风险、回退和所需授权。**本补充是研究与规划交接，不是立即实施指令。** 先把当前机制和最小可行调整讲清楚，再单独确认实施范围；不以 CI 大改阻塞 4.2 的视觉与交互研究。
