# 一、负责人决定

正式采纳 Claude Opus 5.5 最新 CI 架构评审的主要整改方向。

总体结论：

**Accept with Changes — 保留现有 CI，集中修复可信度、覆盖粒度与证据验证问题。**

本轮目标不是重新建立一个 CI 平台，而是让现有 Moody Blues 能够准确回答：

1. 应当执行的检查是否全部执行？
2. 实际执行的每个必要用例是否通过？
3. 是否运行了正确的代码、组件与渲染路径？
4. 测试结果是否拥有完整、可核对的证据？
5. 证据是否属于当前源码与当前 CI 运行？
6. 最终合入代码是否就是经过对应验证的代码？
7. CI 本身是否具备检测误放行的能力？

**CI 绿色必须有可核对的依据。**

不允许以删除断言、缩减覆盖、忽略失败或隐性降级的方式取得 PASS。

# 三、工程语言原则：TypeScript First

本轮正式采用：

**TypeScript First, JavaScript By Exception。**

具体要求：

1. 新增或实质性重构的第一方 CI 管理逻辑优先使用 TypeScript。
2. Evidence Gate、Expected Catalog、身份合同、证据 Schema 与测试调度的新核心逻辑优先具备静态类型。
3. 建议使用严格 TS 类型约束，减少结果状态、Schema 和身份字段之间的隐式错误。
4. 现有 `.cjs`、`.mjs` 不要求机械地全部迁移。
5. 允许保留少量必要的 CommonJS / Node 启动桥接。
6. 必须保证 CI 能在全新环境中可靠自举，不能出现“必须先运行尚未构建的 TS 工具才能完成依赖安装”的循环。
7. 使用 JS 的例外应有明确的 Node 兼容、工具链或启动原因。

如果当前 Node、构建器或测试环境对某种 TS 运行方式存在限制，应选择经过验证的编译或执行方案。

**语言统一不得削弱 CI 的可靠性。**

# 四、最高优先级：修复误放行

## 4.1 必需证据遗漏仍然 PASS

此前已经复现：

- 单项结果合法；
- 汇总 JSON 增长后超过上传预算；
- 必需汇总文件被 omitted；
- CI 仍可能 PASS。

必须修复。

正式要求：

- 区分 Required Evidence 与 Optional Diagnostics；
- 必需文件缺失、非法、身份错误、Hash 错误或超限时不得 PASS；
- 可选证据缺失应登记原因；
- Summary 应采用紧凑索引，必要明细合理分片；
- 上传准备与最终门禁结果必须关联；
- 不允许只检查已成功生成的证据，而忽略预期必需集合。

**这是已确认的缺陷，应立即实施失败关闭。**

## 4.2 验证真实上传结果

本轮采纳 Claude 最新修订：

**将现有独立 Gate Job 升级为下载证据并复核的第二道防线。**

不另建独立 Judge Runtime。

建议结构：

```text
测试执行
   ↓
结构化结果收集
   ↓
Evidence Summary
   ↓
Manifest / Seal
   ↓
上传 Evidence Core
   ↓
独立 Gate Job 下载
   ↓
身份、Hash、覆盖与状态复核
   ↓
最终 PASS / 拒绝
```

独立 Gate 至少检查：

- 当前运行身份；
- Manifest Hash；
- 预期必要用例覆盖；
- 所有必要用例结果；
- 完整封存标记；
- Profile 身份；
- 上游必要 Job 的实际结论。

上传失败应按 Claude 最新建议归为：

**ERROR — evidence_upload**

不能被标记为 PASS。

如果产品断言已经确认失败，但存在证据缺损，保留 FAIL 主状态并显式报告 `evidence_incomplete`。

# 五、从脚本级检查升级为用例级覆盖

这是 Claude 最新报告中最值得优先研究的风险。

目前标准 Browser Suite 的顶层清单有 31 个脚本。

但脚本退出码为 0，不自动证明它内部所有预期场景都执行了。

可能存在：

- 内部场景未运行；
- `skip`；
- 条件提前返回；
- 空循环；
- 功能探测后跳过；
- 断言未执行；
- 部分异步任务未正确等待。

这些目前属于需要结合源码核查的风险，不应在未复现时直接宣布所有脚本存在缺陷。

## 5.1 用例 ID

建立稳定的用例或合同 ID。

对于实际具有多个行为场景的脚本，应能够报告内部场景：

- ID；
- 是否实际执行；
- PASS / FAIL / SKIP / BLOCKED；
- 执行耗时；
- 目标失败签名；
- 必要检查点；
- 实际运行路径或能力档位。

不能只用整个脚本的退出码代表所有内部合同。

## 5.2 生成式 Expected Lock

采纳 Claude 最新建议：

**测试声明是输入，Expected Lock 是受版本管理的审查产物。**

推荐：

`测试声明 → 自动生成 → expected.lock.json → CI 重新生成并比较`

要求：

- 不建立需要人工维护两份内容的中央清单；
- 用例增删必须反映在锁文件 Diff；
- CI 重新生成结果与已提交锁文件不同时拒绝通过；
- 记录适用 Profile 与合同分类；
- 防止零用例或错误跳过取得成功。

如果现有测试结构不支持直接提取内部用例，应采用适当的测试框架或薄上报辅助函数逐步迁移。

不要为了统一所有旧脚本而一次性重写全部测试。

## 5.3 删除断言的风险

Expected Lock 能发现用例目录变化，但无法独立证明某个用例内部的关键断言仍然存在。

因此，对于核心合同，应结合：

- 精确反例；
- 故障注入；
- 断言或检查点下限；
- 定向变异测试；
- 代码审查。

不能把 Expected Lock 描述成能够防止所有测试绕过。

# 六、调整 Fail-fast

根据 Claude 的建议，按阶段区分。

## 6.1 保留 Fail-fast

适用于：

- 依赖安装；
- 基础类型检查；
- 必要构建；
- 依赖前序产物的打包。

这些阶段失败后继续运行通常没有价值。

## 6.2 Unit / Browser 尽可能完整执行

独立的行为检查应在整体预算允许范围内继续执行。

不应因为第一个无关测试失败，就永久遮蔽后面的独立失败。

只有具有真实依赖关系的测试，才应因前置失败标记 BLOCKED。

### 时间预算

整体剩余时间不足时，可以停止调度新测试。

未运行的测试必须记录为 NOT_RUN 或等价的非通过状态。

**不能将剩余测试未执行的运行总结为完整 PASS。**

## 6.3 随机顺序研究

建议为独立行为测试增加受控随机顺序检查，用于发现隐式测试依赖。

固定随机种子并保存为证据。

该类高成本检查可安排在专项或周期性运行，不必全部放入每次标准 PR 检查。

# 七、强化源码与合入身份

## 7.1 保留现有身份能力

现有 Evidence Runner 已具有：

- HEAD；
- Git Tree；
- 工作区 Dirty；
- 源码内容 Hash；
- Lockfile Hash；
- Run ID；
- Attempt；
- 环境版本等字段。

不得重复建设第二套不兼容的身份服务。

可补充：

- Runner 镜像身份；
- Profile；
- Expected Lock 身份；
- 构建参数；
- 实际渲染器信息；
- 构建结束后的源码状态。

## 7.2 Git Tree 与合入资格

Claude 建议以 Git Tree 作为源码内容身份的重要判据。

本轮采纳这一研究方向，但应同时保留：

- Commit SHA；
- PR Head；
- Base；
- 实际受测合并身份；
- Workflow；
- Run ID / Attempt；
- 必要的工具链及测试合同身份。

**不能只凭 Tree 相同就忽略工作流、依赖或测试合同是否变化。**

若设计正式 PR Gate，需要证明本次证据适用于实际将被合入的代码及对应验证条件。

## 7.3 并发与取消

重点检查：

- main Push 是否可能因新运行而取消旧验证；
- PR 与手动运行是否可能共享冲突的 Concurrency Group；
- Gate 是否使用正确的 `if` 与 `needs`；
- Job 跳过能否误导保护规则；
- 超时是否被错误归类为正常取消。

可按核查结果修复工作流中的明确设计错误。

但本轮不得自行修改 GitHub 分支保护、必需检查名称或 bypass 策略。

# 八、实际渲染路径与质量档位

这是 Claude 特别强调的新风险。

如果测试需要验证 WebGL 或高品质材质，却实际运行在 Canvas/CSS 兼容路径，CI 可能产生错误的覆盖结论。

## 8.1 先核对现有实现

请检查：

- 当前哪些正式或研究场景使用 WebGL；
- 哪些仅使用 Canvas2D、CSS 或 SVG；
- 是否确实存在自动质量档位或技术降级；
- 浏览器环境如何报告 GL 支持；
- 实际测试运行了哪一种渲染路径；
- 测试是否可能在某些能力不可用时提前跳过。

**不得因为 Claude 提到 WebGL，就认定本项目已经大量使用 GL。**

## 8.2 运行路径证据

对声明验证特定渲染技术的测试，应记录：

- 实际 Renderer；
- 实际图形能力；
- 实际技术路径；
- 必要时记录 WebGL 版本及 Renderer 字符串；
- 当前测试环境限制；
- 实际是否命中目标路径。

若测试声明必须验证 WebGL，而环境无法提供：

**不得将 CSS/Canvas 路径的 PASS 伪装成 WebGL 验收通过。**

应标记目标路径未验证，并保留可用环境中的相关验证任务。

## 8.3 与产品纲领的关系

Soft & Wet 4.0 不以自动降低默认画质作为产品要求。

CI 增加质量路径验证，不意味着授权开发自动降档系统。

本轮只要求测试报告诚实描述实际验证了什么。

# 九、可复现构建的强化

现有 Package Contract 和两次构建对照应保留。

Claude 建议进一步研究构建隔离。

具体包括：

- 第二次构建是否复用第一次的缓存；
- 是否共享输出目录；
- 是否存在路径依赖；
- 时区、Locale、Umask 是否影响结果；
- 构建收据是否与 ZIP 字节比较互相冲突。

## 9.1 保留严格比较

同一锁定工具链下的两次独立构建，继续验证字节级一致性。

## 9.2 独立运行条件

如现有构建测试不足以证明真正独立，应研究：

- 清理必要缓存；
- 独立工作目录；
- 改变非语义环境；
- 重新生成产物。

具体改动以证据为准，不机械制造对构建没有意义的变量。

## 9.3 身份不得破坏可复现性

Run ID、构建时间等易变信息，优先保存在构建收据与旁路证据中。

不得因为把动态身份写进 ZIP，又被迫取消原有字节一致性验证。

# 十、研究 CI 解耦

Claude 建议研究 CI 按实验族拆分。

本轮允许实施合理拆分，但应先检查当前真实依赖。

候选实验族：

- 动画与交互；
- 球体与 Hub；
- 设置窗口；
- 环境及天气材质；
- 其它专项研究。

目标是：

- 无关实验不互相阻断；
- 每个实验族具有自己的证据；
- 最终研究 Gate 能准确汇总；
- 保留足够视觉证据；
- 不因某项探索失败而谎称所有研究通过。

## 10.1 研究成熟度

采用三个级别：

**Exploratory：** 可以失败，但必须真实报告。

**Candidate：** 失败阻断所在实验族。

**Contract：** 经过确认成为正式回归要求，迁移到 Standard。

## 10.2 正式产品回归

设置、原生窗口和生命周期等已经成为稳定产品合同的测试，不应长期只依赖研究分支 Push。

请核对标准覆盖并将确认缺失的正式合同迁入正确检查路径。

不要仅为增加清单数量重复运行已经具有等价覆盖的检查。

# 十一、证据封存与状态模型

继续采用五态：

- PASS；
- FAIL；
- ERROR；
- UNVERIFIED；
- CANCELLED。

并记录详细 Reason Code。

最新调整：

- 确认的产品错误：FAIL；
- 基础设施与上传故障：ERROR；
- 确定性证据或预期集合缺陷：UNVERIFIED；
- 人工或并发取消：CANCELLED；
- 实际超时：按来源记录 ERROR(timeout)，不伪装成人工取消。

`BLOCKED`、`NOT_RUN` 属于用例或阶段结果，不得作为完整通过。

`PARTIAL` 如保留，仅作辅助说明，不得代表成功状态。

## 11.1 封存

Evidence Manifest 应明确标记最终内容已完成。

只有被完整收集、核对并封存的证据，才能作为相应阶段的通过依据。

研究运行取消后留下的部分文件，可以用于诊断，但不能冒充正式完整通过证据。

# 十二、门禁自身的测试

保留既有 12 项门禁反例，并增加 Claude 本轮发现的重点：

1. Gate 由于上游失败而错误跳过；
2. 必需证据未封存；
3. WebGL 测试实际运行在其它路径；
4. 构建或测试后源码工作区意外变化；
5. Expected Lock 与实际声明不一致；
6. 实际 Case 数量低于最低要求。

建议进一步研究：

- 属性或性质测试；
- 随机证据损坏；
- 定向变异测试；
- Workflow 静态校验；
- 精确失败签名。

可以使用成熟工具。

不要求为显示“先进”而新增大量无收益的测试依赖。

核心验收是：

**任何必需条件不成立，都不能获得 PASS。**

# 十四、Product / Build / Artifact 身份原则

参考 Claude 的建议：

| 身份 | 用途 |
|---|---|
| Component Version | 当前组件产品身份 |
| Protocol Version | 组件通信及兼容 |
| Build Identity | 实际源码与 CI 运行 |
| Artifact Identity | 最终制品字节来源 |

永久 Project ID 属于可选能力。

只有存在真实的外部稳定标识需求，才需要增加。

不为解决历史版本硬编码问题而强制生成永久 UUID。

版本升级不能无故导致 CI 失败，但真实版本错配仍然必须能够被检测。

# 十五、实施顺序
