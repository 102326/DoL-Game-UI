## 一、已确认的方向与阶段决策

**我们愿意将 Soft & Wet 3.0 — Stone Free 作为一次大型 UI 创新工程来研究，但决定等 Paisley Park 6.0 White Snake 完成后，再正式进入大规模设计定型、源码重构与框架实施。**

这不是取消研发，也不是降低目标。现阶段可继续交流构想、记录技术假设、收集既有代码与生态资料；不提前启动一个持续扩张的新 Framework Runtime，不将讨论结论伪装为已验收的能力。

长期愿景是：

**让 Mod 作者创造可维护的界面能力，让多个愿意参与的 Mod 通过公开合同协作，让玩家自主组织阅读、信息与操作空间。**

我们的研发原则仍是：

**「Mod，本就是创新。」**

允许高价值、高不确定性的探索与必要的大规模重构，也允许留下有用证据的失败；正式交付仍需维护业务正确性、第三方边界、回退与玩家数据。

## 二、三方已经基本对齐的内容

1. **Stone Free 不只是 Widget 编辑器。** 玩家希望获得空间、信息、输入方式与阅读节奏上的自由。悬浮球、Action Dock、工作区、语义缩放、对象比较、阅读回顾、新场景视图等均可保留为能够被反证和替换的研究候选，而非已承诺功能清单。
2. **保留 DoL 业务，不等于保留其全部旧界面形态。** 对来源与语义可验证的业务能力，可以研究新的 Vue 视图；对未知机制、未参与协议的第三方内容保留原状或局部退让。
3. **Framework 的目标是可靠的公共参与能力。** 官方 Stone Free UI 可以成为消费者，而不是 Framework 的隐藏前置条件；但独立仓库、独立 ZIP、独立发布与公共价值是不同问题。
4. **Vue-first，而不是重新发明游戏加载器。** 优先使用 Vue 3、TypeScript、Vite，复用 SugarCube、ModLoader、MapleBirch 的实际能力。公共 Host 合同尽量不暴露 Vue 私有对象；首轮无须支持多个前端框架。
5. **Host 是可靠性基础；Contribution Protocol 是长期核心研究方向。** “可选”仅指第三方接入义务，不意味着协作研究优先级低。
6. **Factory 是作者生产力工具的候选，不是第二套运行时。** 工厂要降低 DoL 特有的接入、构建、验证、二次修改与升级成本，而不是仅复制几个 Vue 文件。
7. **允许真正有依据的结构性改造。** 不能为了避免工程量而长期复制页面级生命周期补丁；也不能仅因版本宏大便先造平台。

上述为方向性共识；尚不构成 Host、SDK、Provider、Factory 的固定包数量或 API Schema。

## 三、建议保留的概念架构：职责，而非预设产品数量

### 3.1 Host / Vue SDK：可靠加入 DoL

- Host 管理公开参与者标识、容器归属、挂载、失效、幂等释放与能力查询。
- 区分 Passage 内临时实例、跨 Passage 持久实例、当前业务绑定、布局偏好等不同寿命；异步初始化和局部 DOM 替换不得复活旧对象。
- Vue SDK 提供 SFC/TS、独立 Vue App 的装载与卸载、资源清理和可重复的构建/加载配方。共享 Vue Runtime 与 Mod 自带 Vue 是待比较的分发方案；默认不强制所有 Mod 共用一个 Vue App、Pinia 或官方主题。
- 不整体代理或复制 DoL State 以冒充完整响应式写入监控；提供来源、时点、有效性明确的按需读取或领域投影。

### 3.2 Contribution Protocol：自愿参加，但长期重点投入

- 允许作者声明可贡献的信息、视图、受支持命令、放置能力、激活/焦点需求与释放方式；玩家所选的 Surface/布局提供者按支持范围组织它们。
- **第三方仅使用 Host / Vue SDK 完全合理**，不必强制参与 Stone Free 的布局系统；未参加协议的 Mod、原版输入和未知 DOM 不应受到默认全局接管。
- 协议仅管理参与者主动交付的资源；先验证两个已参加 Mod 对同一快捷键、模态焦点、界面区域的冲突协商，不立即设计全页面 Input Manager 或中央业务执行器。
- 正向协商成功还不足够：必须包含原版输入框、IME、原生快捷键和未参与 Mod 正常工作的负对照。
- 协调的是 UI 参与关系，并不额外赋予调用原版业务的权限；动作仍由有效、受审的领域适配器连接，不凭按钮文案猜测语义。

### 3.3 Domain Adapters / Layout Providers：公共接缝与具体政策分离

- 领域适配解释指定 DoL/Mod 来源、业务信息和当前有效动作，记录版本与失效范围；不在 Framework 中重做购买、换装、战斗和存档逻辑。
- 可选布局/Surface 提供者负责停靠、浮层、模态层级、焦点恢复、用户偏好及区域尺寸约束。公共协议不应强制继承 Stone Free 的视觉语言。
- 实际要保留“同一能力、多种呈现”：详情/摘要/比较视图可共享来源，局部筛选和滚动仍可独立；同一次用户操作不得因重复事件绑定或入口代理而被意外重复派发；不同入口的独立用户操作是否允许执行，由当前业务合同决定。此处不承诺跨故障全局 exactly-once，也不引入全局业务锁。

### 3.4 UI Factory：开发期工具链，而非玩家运行依赖

- **源码归作者。** Factory 产出可修改的 Vue/TS/SFC、样式、明确依赖、对应 ModLoader ZIP 打包配方、代表性预览样本和按实际功能生成的测试。
- 通用生命周期与接入修复属于版本化 SDK；Factory 可以记录配方及生成来源，协助对比升级，不覆盖作者已改写的源码。
- “任意 Vue SFC 自由修改”与“任意改动都可无损回到画布”不能同时承诺。优先研究源码为真源、受支持参数可视化编辑；可选受限设计文档适合标准设置页等场景。
- 必须对照已有 Vite 模板、Component Lab、Codex/Skill 工作方式，比较首次开发、第二次修改、SDK 升级、故障排查和真实加载成本。不要因为 Factory 能生成文件，就把它宣布为独立产品。
- Stone Free 应真实使用公共合同；**不要求所有已成熟官方组件都改为 Factory 生成物**。

### 3.5 Stone Free：玩家体验旗舰，而不是框架 Demo

官方 UI 专注阅读、信息、操作和个人工作区。悬浮球、Action Dock、Widget、场景新视图、语义缩放、布局预览、跨设备适配和局部恢复，都可以作为有价值的候选。

必须提供不编辑也好用的默认体验；不能因抽离框架而把玩家体验开发无限后移。

## 四、仍须共同研究的设计取舍

| 议题 | 当前倾向 | 仍未取得的证据 |
|---|---|---|
| Framework 的产品独立性 | 逻辑和运行独立作为明确目标；安装、仓库、版本是否独立再决定 | 无官方 UI 的真实第三方任务和维护收益 |
| Host 与 Contribution 优先级 | Host 解决可靠性；Contribution 是更具差异化的长期研究方向 | 不侵入原版前提下的跨 Mod 协商与玩家收益 |
| Vue Runtime 分发 | 比较共享 Runtime + 独立 App 与各 Mod 自带 Vue | 真实离线 ZIP、版本、体积、失败隔离与升级成本 |
| 动作/来源语义下沉程度 | 公共句柄合同 + 受审领域适配 | 当前动作的可靠身份、失效、回调与业务结果证据 |
| 可选布局与多提供者 | 先一个真实提供者；不预建全局布局仲裁器 | 多 Mod 空间冲突及提供者替换需求 |
| Factory 产品形态 | DoL 专业配方、源码和验证优先；可视化工作台可探索 | 是否优于模板 + Agent，以及可编辑源码如何升级 |
| 旧 UI 页面编排层 | 允许替换有证据的耦合点，保留正确的业务适配与回退 | 真实源码基线、双消费者原型与回归 |

**不要把“研究起点”解读为长期能力天花板，也不要把“长期目标”提前写成 3.0 已确认发布功能。**

## 五、两条独立的核心验证结论

### A · 独立开发价值

在没有 Stone Free 官方 UI、私有 Store、官方样式和私有 import 的前提下，一位作者能通过公开合同创建、运行、修改、升级并维护一个实际有用的 Vue Mod。

验证临时/持久实例、局部更新、真实 Mod ZIP、失败/释放及版本缺失行为。

**A 成功仅证明 Framework/SDK 的独立开发价值，不等于 UI 生态已形成。**

### B · 跨 Mod 组合价值

一个业务能力提供者公开可解释的信息/动作合同，另一个作者能够在不同 UI 外壳中合理使用；当第二个视图提出原提供者未预设过、且落在公开能力范围内的新需求时，不必修改提供者私有代码，也不需要双方逐对写兼容补丁。

同时测试两个明确参与协议的 Mod：模态焦点、Escape、快捷键、区域占用、场景失效、提供者缺席；尤其核对**参与者协商成功、原版输入却被影响**的反例。

最后判断玩家在阅读、比较、操作、返回过程中的实际收益。

**B 成功证明协作原型有价值，不自动证明 Framework 已具备完整运行独立性，也不代表社区已经形成生态。**

| 实验结果 | 可以作出的结论 |
|---|---|
| A 通过，B 未通过 | 获得有价值的独立 SDK；不得宣称协作生态成立 |
| B 通过，A 未通过 | 获得有价值的协作原型；不得宣称独立 Framework 成立 |
| A、B 都通过 | 对开放公共框架形成较强技术依据；仍须观察真实作者的持续采用和维护 |
| 两者未通过 | 重新设计职责与技术路线；保留有用的夹具、负面证据和成熟 UI 成果 |

## 六、建议的候选研究实验（White Snake 6.0 后正式启动）

1. **独立消费者：** 不装官方 UI，使用公开 Host + Vue SDK 完成真实面板，并从发布产物构建，验证没有隐藏私有依赖。
2. **能力复用：** 同一来源分别在独立界面、Stone Free 和第二作者的新视图使用；新需求不依赖修改提供者私有业务。
3. **协作冲突：** 两个参加协议的 Mod 竞争焦点、快捷键和区域，包含原版输入、未参加 Mod 的负对照。
4. **Factory 的第二次修改：** 生成 → 作者自行改动 → 配方/SDK 升级 → 对照回归；和模板 + Codex/Skill 比较，而非只计生成速度。
5. **真实玩家任务：** 阅读 → 查看状态 → 比较对象 → 执行动作 → 返回原阅读位置，比较当前 UI、可组织工作区与全新语义视图；检验手机、平板、PC 的代表环境。
6. **重构可行性：** 如旧页面壳重复绑死位置和业务，建立受控替代原型，核对生命周期、输入、状态与原版回退，允许有证据的大规模替换。

首批可选择最能区分假设的实验，不强制一次完成全部，也不以每个实验只用两个组件作为能力上限。

记录何处为静态推断、夹具证据、真实 DoL 结果和未验证项。一般研究中的未知或不确定结果不自动等同于 GER Effect Ledger 的 Unknown，也不据此创建持久业务责任。

## 七、正式研发顺序与现在的工作边界

### 现在至 White Snake 6.0 完成前

- Paisley Park 5.1 按其独立发布验收收口；6.0 White Snake 保持主研发优先级。
- Stone Free 2.7 继续其既定稳定维护与必要修复，不自动扩张为 3.0 重构。
- 本方向允许继续讨论、收集技术问题、保存设计决策和失败经验；可以利用 White Snake 已验证的知识帮助未来调查。
- **不启动 DoL Vue Framework / Factory / Contribution Protocol 的正式大规模实现，不为其新增 6.0 发布门槛，也不要求 White Snake 为 UI 3.0 提前开发专属功能。**

### White Snake 6.0 完成后

- 固定最新 Soft & Wet / DoL / SugarCube / ModLoader 的真实源码和游戏制品身份。
- 复核现有 `DoLGameUI.ui` API v1、Vue 容器、战斗 Dock、生命周期与恢复实现；**不能将其与管理器的 DMC API 混称**。
- 将上述 A/B 两类价值实验与所需 PoC 作为第一轮工程工作，允许并行。
- 让小鸥、Codex 和项目负责人基于可复核证据决定公共 API 的稳定范围、框架物理拆分、Factory 深度和旧编排层替换方案。
- 发布条件须分别说明框架开发者价值、跨 Mod 协作价值和 Stone Free 玩家体验。未通过的部分可保留为研究，不可用一个 Demo 概括全部生态已经完成。

## 八、定稿后的开放决策与证据要求

本次定稿固定研究愿景、职责方向、A/B 双路线及研发顺序；下列实现问题仍保持开放，不因文件定稿而提前冻结：

1. **公共合同深度：** Contribution Protocol 可选接入、长期高优先级；Host 提供必要归属与失效基础，不预建第二个 SugarCube 或全局 Input Manager。
2. **架构与分发：** Vue Runtime 分发、框架物理拆分、可选提供者与具体公共 API，以真实消费者和实际 Mod 制品证据决定。
3. **价值判断：** A/B 结果分别成立或失败；未预设但位于公开能力范围内的新需求，是扩展性检验，不要求协议支持任意新业务。真实生态仍需要作者持续采用和维护的证据。
4. **Factory 深度：** 保留作者源码、版本化 SDK、配方来源的所有权划分；是否增加可视化工作台，依据相对现有模板与 Agent 工作方式的收益决定。
5. **共存范围：** 不主动接管未参与者，是明确的行为边界；不宣称与所有未知 Mod 必然零冲突。实际冲突须记录具体环境，优先共存，无法可靠共存时局部退让并说明原因。
6. **研发启动：** White Snake 6.0 完成后再固定真实基线、选择工程实验；这些准备不增加 6.0 的强制交付任务。本文件本身不授权现在修改代码、部署、设备实验或发布。

项目负责人、Codex 与独立评审者继续保留依据新证据重新审视、反驳和修订方案的权利。必要的范围变化应明确记录；不能通过改写验收含义把未通过结果宣布为成功。

## 结语

我们希望最终做到：

**一个作者创造的能力，另一位作者无需复制业务就能用于自己的界面；玩家能够把这些能力组合成自己的工作区，同时不要求未参与协议的原版和第三方内容为此改变自身行为。**

这不是“又开发一套 UI API”那么简单，而是研究可扩展、可维护、可协作的 DoL UI 生态。

**「Mod，本就是创新。」**

**本文件确认的是研究方向与阶段边界。正式架构设计和大规模开发，等待 Paisley Park 6.0 White Snake 完成后启动。**

## 附录：最终复核记录

**复核结论：Accept，可作为 Stone Free 3.0 正式规划 V1.0 定稿。**

本次核对未发现需要重新推翻方向的架构冲突。最终稿正确吸收了：

- Contribution Protocol 自愿接入，但属于长期核心研究方向。
- 独立开发价值与跨 Mod 组合价值分别验证、分别表述。
- Factory 不另建运行时，作者源码定制不被模板更新静默覆盖。
- 官方 UI 消费公共合同，但不被要求把全部成熟组件改成生成物。
- 正式大规模研发安排在 White Snake 6.0 完成后；当前不新增实现授权。

定稿整理只作三项技术措辞澄清：防止重复绑定误派发不等于全局 exactly-once；尊重未参与者不等于承诺所有未知 Mod 零冲突；研究未知结果不等于 GER 的持久 Unknown。原第八节评审邀请转为定稿后仍开放的决策，不新增研发方向或发布门槛。
