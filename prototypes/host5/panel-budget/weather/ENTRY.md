# #41 · 首帧能看见，后续继续淡入

**建议把 60% 起步列入家庭设备对照候选。** 新开窗口时，从现有 100 ms 线性透明度轨道的 60 ms 处开始，余下约 40 ms 走到全亮。已经播放的轨道沿当前位置转向，关闭仍走原有 80 ms 退场。选择 60% 是为了能看见内容并留出两三个普通刷新周期供过渡；本轮没有测定最佳起始亮度。

## 同一慢云下的三组开关

研究起点 `b87dbfe`。三组都运行相同的 8 秒云层位移和 C 组实验名额配置。每组 48 次受信任输入，鼠标和 Enter 各 24 次，实际设置控制器和独立中性检查器各半。每一组含 24 次打开、24 次关闭，输入目标间隔 300 ms。三组轮换顺序，在公司 Mac Chromium 153.0.8010.12 的 390 × 820 CSS px 视口采样。

| 方案 | 首个 rAF 可见度 ≥59% | 打开首次样式变化 ms，中位 / P95 | 首帧后仍采到中间透明度 | 关闭首次样式变化 ms，中位 / P95 |
|---|---:|---:|---:|---:|
| 直接显示 | 24/24 | 11.9 / 47.0 | 0/24 | 13.1 / 15.1 |
| 从透明淡入 | 0/24 | 28.9 / 65.1 | 24/24 | 28.7 / 30.8 |
| 从 60% 淡入 | 24/24 | 11.6 / 47.7 | 24/24 | 28.3 / 31.1 |

每次记录布局可见性及计算透明度直到全亮。首次变化指标沿用前轮门槛（打开大于 0.01，关闭小于 0.99 或隐藏）；另以 59% 核对此次 60% 设计目标。候选既让打开的首个样式采样有内容，也留住了可测的后续过渡。rAF 样式读取发生在浏览器绘制之前，不能据此断言屏幕已呈现、文字已被人识别或帧时已在真机改善。

按表中顺序，超过 50 ms 的帧间隔数 / 采样数分别为 0/810、0/812、0/811。Event Timing 的 16 ms 门槛下分别匹配 35、37、33 次输入，其余记作缺测。完整记录保留每次目标处理耗时、输入至前两个 rAF、首个与后续透明度、天气时钟以及帧间隔。

## 交互和边界

两种动效均沿用现有局部 WAAPI 层。本次只在中性页面选择起点；Host、设置控制器和产品默认预算无变更。三个条件均检查天气连续播放、到端反向、独立面板播放中卸载、重新启动天气及 Host 释放。候选另在 320、390 CSS px 上用 Enter 打开和关闭设置，检查焦点进出；关闭期间在 25、75、35、80 ms 连续转向，核对同一动画、相同透明度、焦点与最终状态。独立面板还执行 8 次连续 Enter，并检查回收和横向布局。

**接续建议。** 家庭 Windows 用同操作原速并排看透明、60% 和直接显示，重点看深浅背景下是否显得突然，以及关到一半再打开的连续性。Android WebView 用触摸分别开设置和独立面板，记录设备刷新率，优先用实际屏幕录像或可用的呈现轨迹核对首个可辨识画面。若紧凑的 40 ms 在目标机上只呈现一个端点，可选择直接显示；先消化实测，再决定是否推广。
